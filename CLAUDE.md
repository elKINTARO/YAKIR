## 0. TL;DR для агента

Ядро продукту — **не чат з AI**. Ядро — цикл «зафіксувати конкретний прогноз під час тривоги → через 24 години перевірити, що сталося насправді → накопичити особисту статистику того, наскільки прогнози не справджуються».

AI-співрозмовник — це Фаза 2, і він **навмисно обмежений**, бо необмежений емпатичний чат-бот підкріплює тривожність замість зменшувати її. Якщо якесь рішення в коді вибирає між «зручніше поговорити з ботом» і «структурованіша робота з думкою» — завжди друге.

**Три правила, які не порушуються ніколи:**

1. Дані записів ніколи не залишають пристрій у відкритому вигляді.
2. Прогноз не можна редагувати після створення.
3. Застосунок ніколи не називає себе терапією, не діагностує і не дає гарантій щодо майбутнього.

## 1. Контекст і мета

### Проблема

Тривожність підтримується поведінковим циклом: тривога → пошук заспокоєння → миттєве полегшення → підкріплення переконання, що без заспокоєння сталося б найгірше → наступна тривога сильніша. Класичні щоденники симптомів і емпатичні чат-боти цей цикл **живлять**, бо дають безкінечний доступ до заспокоєння без природних обмежень, які є в людських стосунках.

### Рішення

Замість заспокоєння — **емпірична перевірка**. У момент тривоги користувач записує конкретне передбачення («мене звільнять після цієї зустрічі») і свою суб'єктивну впевненість (85%). Через 24 години застосунок питає, що сталося насправді. За кілька тижнів накопичується персональний доказ: середня заявлена впевненість 74%, реальна частота справджень 9%.

Це механізм із КПТ (behavioural experiment / prediction testing), не винахід. Застосунок лише робить його безтертєвим.

### Цільовий користувач

Фаза 1 — виключно автор. Фаза 2 — автор + 3-5 друзів. Фаза 3 — публічний реліз, і лише за умови, що Фаза 1 показала реальну користь на власних даних мінімум за 2 місяці.

### Критерій успіху MVP

Не DAU і не retention. **Єдина метрика: чи веде автор записи 6+ тижнів поспіль і чи змінилася середня заявлена ймовірність між першим і останнім місяцем.** Якщо ні — гіпотеза хибна, і треба міняти її, а не додавати фічі.

## 2. Продуктові принципи

Мають пріоритет над зручністю, красою та фічами. При конфлікті вимог вирішує цей розділ.

### П1. Мінімальне тертя на вході, свідоме тертя на виході

Зафіксувати епізод — 3 екрани, ≤20 секунд, однією рукою, з голосовим введенням (у стані тривоги друкувати важко). Але «поговорити ще» — навмисно довше і з лімітами.

### П2. Застосунок не заспокоює

Ніде в UI, копірайті чи AI-відповідях не з'являються «все буде добре», «не хвилюйся», «ти в безпеці», «це просто тривога». Замість цього — «що конкретно ти передбачаєш?», «наскільки це ймовірно за твоїм досвідом?», «що ти можеш зробити в наступні 10 хвилин?».

### П3. Невизначеність — навичка, а не проблема

Мета — навчитися витримувати «я не знаю», а не отримати відповідь. UI ніколи не обіцяє визначеності.

### П4. Дані користувача — його і тільки його

Local-first за замовчуванням. Синхронізація — опція, і завжди E2EE. Оператор сервісу технічно не може прочитати вміст.

### П5. Статистика детермінована, LLM — тільки формулювання

Усі числа рахує чистий код, покритий тестами. LLM ніколи не «знаходить патерни» — лише переказує вже пораховані цифри людською мовою. Це запобігає галюцинованим «інсайтам» на вибірці з 8 записів.

### П6. Немає стріків, немає гейміфікації

Ніяких «12 днів поспіль!», бейджів, очок. Стрік створює тиск і провину за пропуск, а провина — паливо для тривоги. Пропущений день не має жодних наслідків в UI.

### П7. Порожній стан — це успіх

Тиждень без записів — імовірно, хороший тиждень. Застосунок не «повертає користувача». Жодних re-engagement пушів. Єдині нотифікації — заплановані follow-up на конкретний запис.

### П8. Застосунок доповнює, а не замінює

В онбордингу і налаштуваннях прямо сказано: це інструмент самоспостереження, не медична допомога. Експорт PDF існує саме для того, щоб віднести звіт спеціалісту.

## 5. Технологічний стек

```
Клієнт:      React Native + Expo (SDK 54+), TypeScript strict
Навігація:   expo-router (file-based)
БД:          expo-sqlite + SQLCipher (плагін useSQLCipher)  ← див. ADR-0002
Ключі:       expo-secure-store (Android Keystore / iOS Keychain)
Стан:        Zustand
Стилі:       Nativewind
Нотифікації: expo-notifications, ЛОКАЛЬНІ (без FCM/APNs у Фазі 1)
Голос:       expo-speech-recognition
Графіки:     react-native-svg вручну
Експорт:     expo-print → PDF, expo-sharing
Тести:       vitest + @testing-library/react-native
             logic (domain/) — покриття 100%

Бекенд (Фаза 2):  Python 3.12, FastAPI, uvicorn. STATELESS. Без БД.
LLM:              Anthropic API, zero-retention увімкнено
```

**Чому саме так:**

- `expo-sqlite` з опцією `useSQLCipher`: прозоре шифрування всієї БД одним ключем без сторонньої нативної залежності. `op-sqlite` був потрібен, поки `expo-sqlite` не вмів SQLCipher; тепер уміє. Деталі — ADR-0002.
- Expo Go не використовується взагалі: SQLCipher, secure-store і офлайн-розпізнавання мовлення потребують нативного коду. Тільки dev client. ADR-0003.
- Локальні нотифікації: працює офлайн і в літаку, без push-токенів, без серверної інфраструктури, без ще одного вектора витоку метаданих.
- Стек навмисно збігається зі стеком Mova (RN/Expo + FastAPI), щоб не платити за перемикання контексту.

## 6. Архітектура даних і безпека

### Фаза 1: сервера не існує

```
┌─────────────────────────────┐
│  Пристрій                    │
│                              │
│  expo-secure-store           │
│    └─ db_key (32 bytes)      │  ← генерується при першому запуску
│         │                    │
│         ▼                    │
│  SQLite + SQLCipher          │
│    ├─ episodes               │
│    ├─ followups              │
│    ├─ exercise_logs          │
│    └─ settings               │
│                              │
│  expo-notifications          │
│    └─ локальні тригери       │
└─────────────────────────────┘
```

**Ініціалізація ключа:**

```ts
// src/db/key.ts
import * as SecureStore from 'expo-secure-store';
import * as Crypto from 'expo-crypto';

const KEY_ALIAS = 'yakir.db.key.v1';

export async function getOrCreateDbKey(): Promise<string> {
  const existing = await SecureStore.getItemAsync(KEY_ALIAS, {
    keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
  });
  if (existing) return existing;

  const bytes = await Crypto.getRandomBytesAsync(32);
  const key = Buffer.from(bytes).toString('hex');
  await SecureStore.setItemAsync(KEY_ALIAS, key, {
    keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
  });
  return key;
}
```

**Правила безпеки Фази 1:**

- `WHEN_UNLOCKED_THIS_DEVICE_ONLY` — ключ не потрапляє в iCloud/Google backup. Втрата пристрою = втрата даних. Свідомий компроміс; резервні копії з'являються у Фазі 3 через E2EE-синк. Попередити в онбордингу явно.
- `android:allowBackup="false"` у маніфесті.
- `expo-screen-capture` → блокувати скріншоти на екранах з текстом епізодів (опційно, вимикається).
- Біометричний замок на вхід — опційний, `expo-local-authentication`.
- Жодного crash-репортера, який може захопити стан. Якщо Sentry — з агресивним `beforeSend`, що вирізає все, крім типу помилки і стектрейсу.

### Фаза 2: бекенд як тонкий проксі

```
Пристрій ──HTTPS──▶ FastAPI (stateless) ──▶ Anthropic API
   │                      │
   │                      └─ ЖОДНОГО запису в БД
   └─ уся історія локально; надсилається в тілі запиту
```

- Сервер не має бази даних. Якщо в коді з'являється `CREATE TABLE` — це помилка архітектури.
- Логи: тільки `request_id`, latency, кількість токенів, код відповіді. **Ніколи** тіло.
- Rate limiting за анонімним device-id (HMAC від installation id), не за акаунтом.

## 7. Схема БД

Міграції — послідовні файли `src/db/migrations/001_init.ts`, кожен експортує SQL рядком. Версія в `PRAGMA user_version`, бамп версії всередині тієї ж транзакції, що й сама міграція. Ніколи не редагувати вже застосовану міграцію.

Розширення `.ts`, а не `.sql`: Metro не збирає `.sql` як вихідний код, а читання їх як ассетів поставило б асинхронний доступ до файлової системи в шлях запуску без жодної вигоди.

```sql
-- 001_init.sql

CREATE TABLE episodes (
  id            TEXT PRIMARY KEY,          -- uuid v4
  created_at    INTEGER NOT NULL,          -- unix ms, UTC
  tz_offset     INTEGER NOT NULL,          -- хвилини від UTC на момент запису
  intensity     INTEGER NOT NULL
                CHECK (intensity BETWEEN 0 AND 10),
  fear          TEXT NOT NULL              -- конкретний прогноз
                CHECK (length(trim(fear)) >= 3),
  probability   INTEGER NOT NULL           -- 0..100, суб'єктивна впевненість
                CHECK (probability BETWEEN 0 AND 100),
  tags          TEXT,                      -- json array, nullable
  followup_at   INTEGER NOT NULL,          -- unix ms
  notif_id      TEXT,                      -- id локальної нотифікації
  locked        INTEGER NOT NULL DEFAULT 1 -- завжди 1
);

CREATE INDEX idx_episodes_created ON episodes(created_at DESC);

CREATE TABLE followups (
  episode_id     TEXT PRIMARY KEY REFERENCES episodes(id) ON DELETE CASCADE,
  completed_at   INTEGER NOT NULL,
  outcome        INTEGER NOT NULL          -- 0=не сталось, 1=частково, 2=сталось
                 CHECK (outcome IN (0,1,2)),
  actual_impact  INTEGER                   -- 0..10, наскільки погано НАСПРАВДІ
                 CHECK (actual_impact IS NULL OR actual_impact BETWEEN 0 AND 10),
  what_helped    TEXT,
  was_late       INTEGER NOT NULL DEFAULT 0 -- 1, якщо заповнено пізніше ніж +48h
);

CREATE TABLE exercises (
  id            TEXT PRIMARY KEY,
  slug          TEXT NOT NULL UNIQUE,
  title         TEXT NOT NULL,
  duration_sec  INTEGER NOT NULL,
  category      TEXT NOT NULL,             -- grounding|breathing|body|cognitive|behavioural
  body_md       TEXT NOT NULL,
  source_note   TEXT                       -- походження методу
);

CREATE TABLE exercise_logs (
  id            TEXT PRIMARY KEY,
  exercise_id   TEXT NOT NULL REFERENCES exercises(id),
  episode_id    TEXT REFERENCES episodes(id) ON DELETE SET NULL,
  started_at    INTEGER NOT NULL,
  completed_at  INTEGER,                   -- NULL = перервано
  relief        INTEGER
                CHECK (relief IS NULL OR relief BETWEEN 0 AND 10)
);

CREATE TABLE settings (
  key    TEXT PRIMARY KEY,
  value  TEXT NOT NULL
);
```

### Інваріанти

- `episodes` — **append-only**. Жодного UPDATE, окрім `notif_id`. Немає екрана редагування. Видалення епізоду — тільки з налаштувань, не свайпом зі списку.
- Один епізод → максимум один follow-up.
- `tz_offset` зберігається окремо: статистика по часу доби рахується в локальному часі **моменту запису**, а не поточному.

## 9. Екрани та потоки

### 9.1. Головний екран

Одна велика кнопка «Зафіксувати» в нижній третині (досяжна великим пальцем). Над нею:

- Якщо є **незаповнені follow-up** — картки «Вчора ти передбачав: …» з кнопкою «Перевірити». Найвищий пріоритет на екрані.
- Якщо немає — нічого. Порожній екран. Без мотиваційних цитат, без «як ти сьогодні?».

Таб-бар: Головна, Вправи, Статистика, Налаштування.

### 9.2. Потік фіксації

**Крок 1 — Інтенсивність.**
«Наскільки сильно зараз?» Вертикальний слайдер 0–10, великий, haptic на кожній поділці. Без текстових ярликів типу «панічна атака» — тільки цифри й колірний градієнт.

**Крок 2 — Прогноз.**
«Чого конкретно ти боїшся, що станеться?»
Плейсхолдер: _«Не "мені тривожно", а що саме має статися. Наприклад: "на зустрічі скажуть, що я не тягну проєкт"»_
Мультирядкове поле + велика кнопка мікрофона.
Валідація: мінімум 3 символи. Якщо текст схожий на опис стану, а не події — м'яка підказка, але **не блокувати**. Ніколи не блокувати вихід із потоку через валідацію.
Опційно: чипси-теги (робота, здоров'я, стосунки, гроші, соціальне, майбутнє, інше).

**Крок 3 — Впевненість.**
«Наскільки ти зараз віриш, що це станеться?» Слайдер 0–100%, крок 5, число крупно.

Після збереження — підтвердження на 2 секунди: «Записано. Завтра о {час} перевіримо, що сталося.» Дві кнопки: «Готово» / «Хочу вправу зараз» (веде в бібліотеку, передає `episode_id`).

**Чернеток немає.** Вихід на кроці 2–3 → епізод зникає. Причина: неповний запис (інтенсивність без прогнозу) — це моніторинг симптомів без терапевтичного компонента, тобто саме те, чого ми уникаємо.

### 9.3. Follow-up

Зверху великим шрифтом — **дослівний текст прогнозу** і дата. Під ним: «Ти оцінював це у {probability}%».

Три питання на одному екрані:

1. «Що сталося?» — три великі кнопки: _Не сталося_ / _Частково_ / _Сталося_
2. Якщо «Частково» або «Сталося»: «Наскільки погано вийшло насправді?» слайдер 0–10
3. «Що допомогло тобі тоді?» — необов'язкове поле

**Після збереження** — рефлексивний блок, згенерований детерміновано:

- `outcome = 0`: «Прогноз не справдився. Це {N}-й такий випадок із {M}.»
- `outcome = 2` і `actual_impact < intensity`: «Сталося — але за твоєю оцінкою це виявилось легше ({actual_impact}/10), ніж відчувалося тоді ({intensity}/10).»
- `outcome = 2` і `actual_impact >= intensity`: «Сталося, і було справді важко. Ти це пережив.» — без спроби переформулювати в позитив.

### 9.4. Вправи

Список за категоріями. Всередині — покроковий гайд із таймером.

**Стартовий набір (seed):**

| slug                 | назва                               | категорія   | ~сек |
| -------------------- | ----------------------------------- | ----------- | ---- |
| `worry-postponement` | Відкладена тривога                  | behavioural | 120  |
| `grounding-54321`    | Заземлення 5-4-3-2-1                | grounding   | 180  |
| `breathing-478`      | Дихання 4-7-8                       | breathing   | 240  |
| `breathing-box`      | Квадратне дихання                   | breathing   | 300  |
| `defusion-thought`   | Розчеплення: «У мене є думка, що…»  | cognitive   | 180  |
| `evidence-check`     | Докази за і проти                   | cognitive   | 360  |
| `worst-best-likely`  | Найгірше / найкраще / найімовірніше | cognitive   | 300  |
| `pmr-short`          | Прогресивна м'язова релаксація      | body        | 420  |
| `physical-discharge` | 20 присідань або швидка ходьба      | body        | 180  |
| `cold-reset`         | Холодна вода на обличчя             | body        | 60   |

Після завершення — «Наскільки полегшало?» 0–10 → `exercise_logs.relief`. Це дає персональний рейтинг того, що працює **саме для тебе**, і згодом сортує список.

**Формулювання в текстах вправ:** жодна вправа не подається як спосіб «прибрати тривогу». Тільки «пережити хвилю», «повернути увагу в тіло». Різниця принципова: перше — уникання, друге — толерування.

`worry-postponement` стоїть першим навмисно: найсильніша вправа для румінативної тривоги, але найменш очевидна. «Запиши тривогу. Признач їй час — сьогодні о 19:00, 15 хвилин. До того часу вона почекає.»

### 9.5. Статистика

Порядок блоків — за терапевтичною цінністю, не за «крутістю графіка».

**Блок 1 — Калібрування (головний).** Якщо `n >= 10`:

```
Твої прогнози
Середня заявлена впевненість:  74%
Справдилось повністю:           9%  (2 з 23)
Справдилось частково:          22%  (5 з 23)
```

Якщо `n < 10` — замість цифр: «Ще {10 − n} перевірок, і тут з'явиться твоя статистика прогнозів.» **Не показувати числа на малій вибірці** — одне справджене передбачення з трьох дасть «33%» і підкріпить тривогу замість спростувати.

**Блок 2 — Прогноз vs реальність.** Скатерплот: X = заявлена ймовірність, Y = фактичний результат (0/0.5/1). Діагональ = ідеальна калібрація. Візуально видно систематичне переоцінювання.

**Блок 3 — Інтенсивність vs фактичний вплив.** Для епізодів, де подія таки сталася: середня `intensity` при фіксації проти середнього `actual_impact`.

**Блок 4 — Календар місяця.** Теплова карта: колір = максимальна інтенсивність за день, порожній = немає записів. Тап → епізоди дня.

**Блок 5 — Що допомагає.** Топ вправ за середнім `relief`, мінімум 3 використання для потрапляння в рейтинг.

**Блок 6 — Час доби і теги.** Гістограма по годинах (локальний час запису, через `tz_offset`) і розподіл за тегами.

### 9.6. Налаштування

- Вікно нагадувань (за замовчуванням 10:00–20:00)
- Біометричний замок on/off
- Блокування скріншотів on/off
- Експорт: PDF-звіт за місяць, JSON-дамп
- Видалити всі дані (подвійне підтвердження)
- Про застосунок: дисклеймер, ресурси допомоги, походження методів

## 10. Логіка нотифікацій

Уся логіка планування — чисті функції в `src/domain/scheduling.ts`, покриті тестами.

**Знак часового поясу.** `tz_offset` — хвилини на схід від UTC, тобто Київ влітку це `+180`, а `local = utc + tz_offset × 60000`. Це протилежний знак до `Date.getTimezoneOffset()`, який для того самого місця дає `−180`. На межі з платформою значення інвертується.

### Правила

1. Базовий час: `created_at + 24h`.
2. **Затискання у вікно.** Якщо базовий час поза вікном (10:00–20:00 локального часу) — зсунути **вперед** до найближчого відкриття вікна. Епізод о 02:30 → follow-up наступного дня о 10:00. Епізод о 22:15 → через день о 10:00. Зсув ніколи не робиться назад: інакше про день питали б раніше, ніж він скінчився, і проміжок був би менший за добу.
3. **Дедуплікація.** Якщо на той самий 30-хвилинний слот вже є заплановані follow-up — зсунути на +30 хв. Максимум 3 нотифікації на день; решта збирається в одну зведену: «Є {N} прогнози для перевірки».
4. **Дедлайн.** Якщо follow-up не заповнено протягом 48 год від запланованого часу — нотифікація скасовується назавжди. Картка лишається на головному екрані, її можна заповнити вручну з позначкою `was_late = 1`. Пізні відповіді **виключаються з калібрування** (пам'ять спотворюється), але лишаються в календарі.
5. **Тиша.** Жодних інших нотифікацій. Ніяких «давно не заходив», «як справи сьогодні», «спробуй нову вправу».

### Крайові випадки

| Ситуація                                     | Поведінка                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Зміна часового поясу між записом і follow-up | Перепланувати всі майбутні нотифікації при `AppState → active`, якщо `tz` змінився                                                                     |
| Нотифікації вимкнено в системі               | Не блокувати роботу. Картки на головному екрані самодостатні. Один раз показати м'яку підказку.                                                        |
| 5 епізодів за годину                         | Усі зберігаються. Follow-up дедуплікуються за правилом 3. **Жодних лімітів на кількість записів** — обмежувати фіксацію означає змушувати замовчувати. |
| Пристрій вимкнено на момент нотифікації      | Доставка при вмиканні в межах TTL; інакше спрацює правило 4                                                                                            |
| Перевстановлення застосунку                  | Дані втрачені (Фаза 1). Явно попередити в онбордингу.                                                                                                  |

## 11. Логіка статистики

`src/domain/stats.ts` — **чисті функції, покриття тестами 100%.** Це серце продукту; помилка тут = хибний висновок про власне життя.

```ts
export const MIN_SAMPLE = 10;

export interface CalibrationResult {
  n: number; // валідні follow-up (was_late = 0)
  meanStatedProbability: number; // 0..100
  fullyOccurredRate: number; // 0..1
  partiallyOccurredRate: number;
  overestimationGap: number; // meanStatedProbability/100 − fullyOccurredRate
  isSufficient: boolean; // n >= MIN_SAMPLE
}
```

### Правила підрахунку

- У калібрування входять **тільки** follow-up із `was_late = 0`.
- `fullyOccurredRate = count(outcome = 2) / n`
- `partiallyOccurredRate = count(outcome = 1) / n`
- Часткові справдження **не** рахуються як справдження в основній цифрі, але показуються окремим рядком. Ховати їх було б підтасовкою на власну користь.
- Опційно (Фаза 2): Brier score = `mean((p_i/100 − o_i)²)`, де `o_i ∈ {0, 0.5, 1}`. Показувати тільки при `n >= 30`.
- Групування по годинах — за `created_at`, зсунутим на `tz_offset` **запису**.
- Рейтинг вправ: середній `relief` серед логів із `completed_at IS NOT NULL`, мінімум 3 записи на вправу.

### Заборонено

- Кореляції, регресії, «ми помітили, що ти тривожишся більше в понеділок». На вибірці в десятки записів це шум, поданий як інсайт.
- Будь-які прогнози майбутнього стану.
- LLM не отримує сирі дані для «аналізу» — тільки готові числа для переказу.

## 12. Фаза 2 — AI-співрозмовник

Додається **тільки** після 4+ тижнів реального використання Фази 1. Якщо Фаза 1 не прижилась — чат не врятує, а зашкодить.

### Роль

Не друг, не психолог, не заспокоювач. **Структурувальник**: проводить через один КПТ-крок і закриває сесію.

### Жорсткі обмеження (не конфігуруються користувачем)

- **Ліміт сесії: 15 хвилин або 20 повідомлень**, що настане раніше. За 3 повідомлення до кінця — попередження.
- **Ліміт на добу: 3 сесії.** При спробі четвертої — не відмова, а редирект: «Сьогодні вже було три розмови. Це ознака, що розмови не знімають напругу. Спробуй {вправа} або запиши прогноз.»
- **Сесія закривається дією**, не згасанням. Останнє повідомлення завжди пропонує конкретний крок.
- Історія попередніх сесій **не** передається в контекст за замовчуванням. Кожна сесія — з чистого аркуша + сьогоднішні записи. Навмисне тертя проти прив'язаності до «того самого співрозмовника».

### Системний промпт (каркас)

```
Ти — структурований помічник у застосунку самоспостереження за тривожністю.
Ти НЕ терапевт, НЕ лікар, НЕ друг. Ти не називаєш себе жодним із цих слів.

ЗАВДАННЯ: провести користувача через один КПТ-крок і завершити розмову
конкретною дією. Не вести тривалу підтримуючу бесіду.

СТРУКТУРА:
1. Що конкретно ти передбачаєш? (події, не почуття)
2. Які докази за? Які проти?
3. Що ти знаєш напевно, а що припускаєш?
4. Що можеш зробити в наступні 10 хвилин?
→ Запропонувати вправу або запис прогнозу. Завершити.

НІКОЛИ:
- Не давай гарантій («усе буде добре», «цього не станеться», «ти в безпеці»)
- Не заспокоюй повторно. Якщо те саме питання втретє — назви це прямо:
  «Ти питаєш це втретє. Заспокоєння дасть полегшення на 10 хвилин
   і поверне тривогу сильнішою. Спробуємо інше?»
- Не діагностуй, не називай стани медичними термінами
- Не вдавай, що пам'ятаєш користувача між сесіями
- Не заохочуй повертатися до розмови; заохочуй дію в реальному світі

ЗАВЖДИ:
- Витримуй невизначеність замість того, щоб її усувати
- 2–4 речення, одне питання за раз, українською

КРИЗА: якщо користувач висловлює наміри самоушкодження — негайно припинити
КПТ-структуру, коротко визнати серйозність, надати контакти кризової допомоги,
запропонувати звернутися до живої людини. Не продовжувати звичайний потік.
Не давати жодних деталей щодо методів.
```

### API

```
POST /v1/session
  body: { messages: Message[], today_context: { episodes_count, last_intensity } }
  → { reply: string, should_close: bool, suggested_action: Action | null }
```

Сервер stateless. `should_close` рахується на сервері за лічильниками з клієнта і **дублюється перевіркою на клієнті** — ліміт не має залежати від довіри до жодної зі сторін.

### Детектор петлі заспокоєння

Детермінований, на клієнті: якщо в межах сесії семантично схожі повідомлення користувача (косинусна близькість embeddings > 0.85; тривіальний фолбек — повтор ключових слів) зустрічаються ≥3 рази — інжектувати в промпт директиву назвати петлю. Не покладатися на те, що модель помітить сама: універсальні моделі до цього не налаштовані, їхні захисти орієнтовані на кризові сценарії.

## 13. Фаза 3 — Синк і публічний реліз

### E2EE-синхронізація

- DEK (ключ шифрування даних) уже існує локально.
- Користувач задає парольну фразу → Argon2id → KEK → шифрує DEK → зашифрований DEK на сервер.
- Сервер зберігає: `user_id`, `encrypted_dek`, `blobs[]` (шифротекст), `updated_at`. **Нічого читабельного.**
- Recovery-код (BIP39, 12 слів) при вмиканні синку — друга обгортка DEK. Без нього втрата фрази = незворотна втрата даних; сказати це прямо, без евфемізмів.
- Конфлікти: епізоди append-only → конфліктів майже немає. Follow-up — last-write-wins за `completed_at`.

### Юридична позиція (обов'язково перед публікацією)

Формулювання визначає регуляторний режим. Різниця не маркетингова, а юридична.

**Можна:** «щоденник самоспостереження», «інструмент для роботи з тривожними думками», «wellness».
**Не можна ніде — ні в описі в сторі, ні в UI, ні на скріншотах:** «терапія», «лікування», «психолог», «психотерапевт», «діагностика», «AI-терапевт», будь-яка обіцянка клінічного результату.

Контекст: станом на середину 2026 щонайменше чотири штати США (Іллінойс, Невада, Род-Айленд, Мен) забороняють AI надавати терапію; низка інших вимагає розкриття AI-природи, протоколів на випадок кризи та захисту даних. Wellness-застосунки й особисте користування під ці заборони не підпадають — саме тому позиціювання критичне. У ЄС заявка на «лікування тривожності» ризикує кваліфікувати застосунок як медичний виріб за MDR.

Перед публічним релізом: політика приватності, умови користування, консультація юриста з профілем digital health. Цей етап не пропускається.

## 14. Безпека користувача

### Дисклеймер

Один раз при першому запуску (з підтвердженням) і завжди в Налаштування → Про застосунок:

> Yakir — інструмент самоспостереження. Це не медична допомога, не терапія і не заміна спеціалісту. Застосунок нічого не діагностує. Якщо тривога заважає жити, працювати чи спати — зверніться до лікаря або психотерапевта; записи з цього застосунку можна взяти з собою на консультацію.

### Кризовий протокол

- Екран «Про застосунок» містить контакти кризової допомоги, **зашиті в застосунок** (доступні офлайн, не тягнуться з мережі). Для України: **Lifeline Ukraine — 7333** (цілодобово, безкоштовно). Перевіряти актуальність при кожному релізі.
- У Фазі 2 — детекція кризових формулювань у чаті з негайним перериванням звичайного потоку.
- Застосунок **ніколи** не генерує і не відображає інформацію про методи самоушкодження, навіть у контексті «чого уникати».

### Незнімні запобіжники

Ліміти сесій чату, `MIN_SAMPLE = 10`, відсутність редагування прогнозів, відсутність стріків. Це не product options. Якщо колись з'явиться користувач, який просить їх зняти — це сигнал, що продукт працює правильно.

## 16. Конвенції коду

- TypeScript `strict: true`. Ніяких `any` — `unknown` + звуження.
- Часові мітки — завжди `unix ms` UTC у БД. Форматування тільки на межі UI.
- Репозиторії повертають доменні типи, не сирі рядки БД.
- `domain/` не імпортує React, RN, SQLite (лінт-правило).
- Тексти UI — тільки через `i18n`, жодних рядків у JSX.
- Conventional commits. Перед PR у `main`: `pnpm test && pnpm typecheck && pnpm lint`.

### Тон копірайту

Друга особа однини, спокійно, без вигуків, без емодзі в системних текстах, без «ти молодець».

- ✅ «Записано. Завтра о 10:00 перевіримо.»
- ❌ «Чудова робота! 🎉 Ти зробив важливий крок!»
- ✅ «Прогноз не справдився. Це 12-й такий випадок із 14.»
- ❌ «Бачиш, все було добре! Не варто було хвилюватися 😊»

## 17. Відкриті питання

Рішення, відкладені свідомо — щоб не вирішувати їх двічі:

- Опційний **місячний** GAD-7? (Ризик: моніторинг симптомів. Користь: об'єктивна динаміка для лікаря.) — відкладено до Фази 2
- Quick Settings Tile на Android для швидкої фіксації зі шторки — бажано, але не в DoD Фази 1
- iOS: Control Center widget (iOS 18+) як аналог QS Tile — дослідити
- Чи давати додавати власні вправи — схиляюсь до «так, Фаза 2», без можливості редагувати вбудовані
